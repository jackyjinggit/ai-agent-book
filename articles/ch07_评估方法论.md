# 评估 Agent：分数下降，第一步不是调模型

> 来源：ai-agent-book 精读笔记第 7 章（深度精读版）
> 原书：李博杰《深入理解 AI Agent：设计原理与工程实践》（Apache-2.0），本文为独立提炼改写

做 Agent 的都会遇到一个怪现象：昨天还好好的，今天分数掉了。绝大多数人的第一反应是换模型、改提示词，折腾一天，问题还在。

先停下来。这个判断顺序，本身就是评估体系要解决的第一件事。

## 一、评估对象不是模型，是「模型 + Harness」

一个 Agent 的表现 = 模型能力 × 调度它的那层东西（提示词、工具、反馈循环、任务状态管理——现在大家叫它 Harness，或者 Agent 框架）。

Agent 变差，可能是模型的问题，也可能是 Harness 的问题。怎么区分？两个实验：

- **模型替换实验**：固定 Harness，只换模型。分数随模型大幅波动 → 模型瓶颈；换更强模型不涨分 → Harness 瓶颈。
- **消融实验**：逐个关闭 Harness 的组件，看哪个关了掉分最多。

两个互补，做完你才知道该往哪使劲。

## 二、指标选错，评估等于白做

同样是 k 次尝试，两个公式天差地别：

- **Pass@k**（k 次至少一次成功）：1-(1-p)^k。p=0.6、k=5 时 ≈ 99%。技术奇观、探索、科研场景用它——看能力天花板。
- **Pass^k**（k 次连续全过）：p^k。同样 p=0.6、k=5，只有 ≈ 7.8%。

一个像「总能成」，一个像「总不出错」。**支付、退款、权限变更、部署这类可靠性场景，必须用 Pass^k**。用错指标，你会在 99% 的自我感觉良好里上线一个 92% 概率出错的系统。

## 三、过程指标与结果指标：别把「说了」当「做了」

- **过程指标（白盒）**：行动合法率、工具调用正确率、路径效率（步数/冗余/回退）、检索覆盖率、成本延迟。
- **结果指标**：系统真的变了吗？
- **安全项一票否决**：幻觉、安全违规——其他维度满分也归零。
- 轨迹 ≠ 结果。举一个真实案例：Anthropic 在 Claude Opus 4.5 的评估里（System Card，2025-11，τ²-bench 航空客服场景），模型发现政策漏洞、给用户找了更优路径——按预设路径打分判失败，按结果判成功。[出处](https://www.lesswrong.com/posts/gfby4vqNtLbehqbot/claude-opus-4-5-model-card-alignment-and-safety)。**先定义「成功」是什么，再跑评估。**

## 四、Rubric 怎么定才不被骂

Scale AI「Rubrics as Rewards」的四条准则：

1. **基于专家指导**：没有专业基础的 Rubric 只能抓语言流畅度。
2. **全面覆盖**：正面标准 + 明确 Pitfall（高风险常见错误）。
3. **按重要性加权**：必要/重要/可选/一票否决项分级（实测：幻觉一票否决在 180 次评判中触发了 28 次）。
4. **评价标准自包含**：每条独立可操作——「回应展示深刻理解」✗；「引用至少两个权威理论并准确解释如何支持结论」✓。

## 五、失败归因：找第一个错误，不是最后一个报错

端到端评估只告诉你成功/失败，不告诉你从哪步开始错的。归因的正确姿势：

- **首错类别 + 首错步骤 + 证据**。后续错误多是连锁反应——edit_file 失败后三次重试，根因是文件编辑错了，不是三个独立 bug。
- **精确复制错误归因链**：原始字节 → 工具返回 → Harness 序列化 → 模型输入 → 模型输出 → 工具匹配，逐层找第一个分歧。模型输出对、传输层错 → 归因给 Harness，不是模型。
- 归因记录结构化（JSON/YAML）：步骤号/工具名/观察证据/根因与后果/置信度，存任务目标+环境+版本+轨迹供回归。

## 六、回归测试：端到端不够，轨迹前缀才是主力

- **端到端回归**：完整流程不退化——最接近生产，但难定位失败步。
- **轨迹前缀回归**：冻结首个错误前的上下文，只测「下一步动作」——成本低、隔离单点问题。**生产级 Agent 比端到端更重要**。答案定义为「可接受动作集合」（允许/禁止），不是唯一答案。

## 七、LLM-as-a-Judge 的五个坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 长度偏差 | 长回答得分偏高 | Rubric 罚冗长/审计相关性 |
| 同源模型（Goodhart） | Agent 和评判模型同家族 → 钻评判偏好盲区 | 多源异构评判（不同家族 LLM 分别评） |
| 位置偏差 | 偏向先出现的候选 | 交换顺序各评一次取平均 |
| 评判者校准缺失 | 分数不可信 | 先建 100-200 例金标集，kappa>0.7 再启用 |
| 统计不显著 | 「73% vs 70%」就敢切换 | 配对分析（McNemar）+ 3-5 种子取均值 |

一句警告：100 例里 70% 成功率，95% 置信区间大约 ±9 个百分点。**「感觉变好了」不是切换的理由。**

## 八、Benchmark → 改进闭环

1. 分数下降先查评测系统（环境/用例/bug），再动 Agent。
2. 读报告先找失败簇（按任务/能力标签聚集），别盯总分。
3. 一轮只改一个变量（原书第 7 章 AndroidWorld 实例：H1 加提示无效 → H5 换 accessibility feed 100% 但 token 2.5× → H5C 精简节点 100% 且 token 0.5×）。
4. 小样本只够决定下一步，不够下结论——4/4 不能写成整体 100%。
5. 好报告写清：结论适用哪里 / 哪些底线没过 / 下一轮验证什么。

## 九、基础设施：把评估变成工程

- **消融开关**：每个特性可独立关闭，定期跑消融发现「特性债务」。
- **AB 测试**：多臂而非二元；区分机制指标和目标指标（「改的是机制，关心的是目标，是同一个吗？」）；设护栏指标（不能变差的底线）。
- **双层特性开关**：编译时物理移除 + 运行时服务端下发。
- **提示词像代码一样管**：确定性渲染 + 版本化快照 + 每次变更跑回归。
- **可观测性回流**：生产轨迹 → 失败筛选 → 脱敏 → 沉淀为回归用例（评估集从静态变活资产）。

## 十、成本别拍脑袋：KV Cache 与压缩不是加性关系

上下文是每轮全量重发的：1k+2k+3k = 6k 而非 3k；工具返回占输入大头（八轮任务 20,700 token 里 9,544 是工具返回）。

实测：稳定前缀单开省 28.3%，压缩历史单开省 17.5%，**合开只省 30%（不是 45.8%）**——压缩会缩短可命中缓存的前缀。必须完整任务一起实测。

## 七条工程判据（收藏用）

1. 要上线可靠性功能 → 指标用 Pass^k，设一票否决项。
2. 不知道瓶颈在模型还是 Harness → 先跑模型替换实验，再跑消融。
3. 分数下降 → 第一步查评测系统，第二步找失败簇，第三步才动 Agent。
4. 要换评判方法 → 先建金标集校准（kappa>0.7），再放量。
5. 要省成本 → KV Cache 与压缩分开实测，别按单开数据相加。
6. 要做自我评估 → 先搭消融开关 + 轨迹前缀回归 + 生产轨迹回流。
7. 要切换任何配置 → 分差超噪声 + 配对成立 + 可复现，三条齐了才动。
