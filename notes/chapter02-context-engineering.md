## 一、核心认知

1. **上下文决定 Agent 的能力上限**——模型再强，喂不进对的上下文就白搭；上下文组织是 Harness 工程的核心战场。
2. **上下文学习本质上是检索而非推理**——把信息塞进上下文只是「检索出来给模型看」，不是模型真的「学会」；这决定了 KV Cache、压缩、检索策略都是架构约束而非优化项。
3. **KV Cache 是架构约束**：稳定前缀可命中缓存，任何扰动前缀的设计（包括压缩历史）都会影响缓存收益——**缓存收益非加性**。
4. **提示工程消融实验**：信息组织混乱导致成功率下降 30% 以上——系统提示词不是「写得好」，而是「组织得好」。

## 二、可操作框架

### 2.1 从 API 视角看上下文结构

- **消息的四种角色**：system / user / assistant / tool——顺序与角色构成 Chat Template，是模型看到的一切
- **Agent 核心循环**：system + user → assistant（含工具调用）→ tool 返回 → assistant……循环直到无工具调用
- **生产代码必须有 max_iterations 上限**——Agent 可能永远重复同一工具调用

### 2.2 KV Cache 与 Prompt Cache（两个层级）

| 层级 | 缓存什么 | 约束 |
|---|---|---|
| KV Cache | 模型内部注意力键值 | 前缀一致才命中；扰动前缀=缓存失效 |
| Prompt Cache | 服务端提示词模板 | 长稳定前缀收益大 |

- **缓存作为架构约束**：稳定不变的放前面（系统提示、工具定义、固定上下文），易变的后置
- **KV Cache 未必一次性**：可编辑、可组合的「笔记」——把 Agent 自己的中间结论作为可复用的缓存块

### 2.3 提示工程要点

- 系统提示词确定性渲染 + 版本化快照 + 每次变更跑回归（像代码 CI）
- **状态显式化**：Agent 状态栏把隐式状态（已用步数、工具计数、当前目标）显式化——但元信息本身可能出错，需可靠性兜底

### 2.4 Skills 渐进式披露

- 工具/Skill 定义不一次性全塞，**按需加载**：Agent 判断需要时才加载完整内容（对抗「工具爆炸」的上下文侧手段）
- 依赖模型元认知：「不知道自己不知道什么」就无法触发加载——这是该机制的边界

## 三、常见坑

1. 上下文累积爆炸（每轮重发全部历史，1k+2k+3k=6k 而非 3k）
2. 压缩/摘要与 KV Cache 叠加，收益按单开数据相加估算（实测非加性）
3. 系统提示词多人长期维护 → 熵增 → 成功率下滑
4. 状态栏元信息不可靠，Agent 基于错误计数做决策
5. 超长 ReAct 循环中思考内容累积（Chat Template 保留机制差异：有的剥离历史思考、有的强制回传）——两种策略利弊不同

## 四、工程判据（决策清单）

- **上下文要优化** → 先画「稳定前缀 / 易变尾部」分布，稳定前移
- **要省 token/延迟** → KV Cache 与压缩分开实测，别相加
- **系统提示词多人维护** → 版本化 + CI 式回归 + 变更评审
- **Agent 卡死循环** → 设 max_iterations + 状态栏可见 + 终止条件
- **工具太多塞不下** → 用 Skills 渐进式披露，别全量灌
