# 精读笔记 · 第 7 章《Agent 的评估》

> 来源：李博杰《深入理解 AI Agent：设计原理与工程实践》第 7 章（本地精读）
> 本文为加工产物：把章节内容提炼为「核心认知 / 可操作框架 / 常见坑 / 工程判据」，供落地实践复用

---

## 一、核心认知

1. **评估对象不是模型，是「模型 + Harness 组合体」**——Agent 表现不佳时，改进方向可能是 Harness（提示词/工具/反馈循环）而非换模型。
2. **区分两类瓶颈的手段是模型替换实验**：固定 Harness 只换模型，分数随模型大幅波动 = 模型瓶颈；换更强模型不涨分 = Harness 瓶颈。与消融实验（关闭 Harness 组件）互补。
3. **评估体系的首要价值不是打分，是让你能快速可靠地跟上变化**——数小时内出切换决策，而不是凭直觉等反馈。
4. **先查评测系统，再动 Agent**——评测 bug/环境资源不足/用例脱节，在数字上跟模型退化一模一样，只有查完整轨迹才能区分。

## 二、可操作框架

### 2.1 评估指标体系（先定口径再谈分数）

| 指标 | 公式 | 含义 | 用在哪 |
|---|---|---|---|
| **Pass@k** | 1-(1-p)^k | k 次尝试至少一次成功 | 技术奇观/探索/科研（能力天花板） |
| **Best@k** | 取 k 次最好 | 连续输出取最优 | 同上 |
| **Pass^k**（consecutive） | p^k | k 次连续全过、一次不犯错 | 支付/退款/权限变更/部署（可靠性） |

> 例：p=0.6, k=5：Pass@5≈99%，但 Pass^5≈7.8%——一个像「总能成」，一个像「总不出错」。**可靠性场景必须用 Pass^k**。

- **过程指标（白盒）**：行动合法率 / 工具调用正确率 / 路径效率（步数、冗余动作、回退次数）/ 检索覆盖率 / 成本与延迟
- **安全与鲁棒性**：幻觉/安全违规 = 一票否决（其他维度满分也归零）；鲁棒性看随机种子敏感性、页面变化适应、API 抖动容忍、长时记忆干扰
- **轨迹 vs 结果双重覆盖**：「说了做了」（轨迹）≠「系统真的变了」（结果）——Anthropic 机票案例：Agent 发现政策漏洞给用户更优方案，按预设路径打分判失败，按结果判成功。**先定义「成功」再跑评估**。

### 2.2 Rubric 四准则（Scale AI「Rubrics as Rewards」）

1. **基于专家指导**：反映领域知识，捕捉核心事实与推理步骤（缺专业基础的 Rubric 只能抓语言流畅度）
2. **全面覆盖**：正面标准 + 明确**陷阱（Pitfall）**（高风险常见错误）
3. **按重要性加权**：必要项/重要项/可选项/**一票否决项**（幻觉否决实证有效：180 次评判触发 28 次）
4. **评价标准自包含**：每项独立可操作，不依赖评价者领域知识——「回应展示深刻理解」✗ →「引用至少两个权威理论并准确解释如何支持结论」✓

### 2.3 失败归因：定位首个错误（不是最后一个报错）

- 端到端评估只给「成功/失败」，不给「从哪步开始失败」→ 归因 = **首错类别 + 首错步骤 + 证据**
- 后续错误只是连锁反应（edit_file 失败后三次重试：主因是文件编辑错误，三次重试是后果不是三个根因）
- 归因记录结构化（JSON/YAML）：步骤号/工具名/观察证据/根因与后果区分/置信度；保存任务目标+环境状态+Agent 版本+完整轨迹供回归
- **精确复制错误归因链**：原始字节→工具返回→Harness 序列化→模型输入→模型输出→工具匹配，逐层找首个分歧——若模型输出对而传输层错，归因给 Harness 而非模型

### 2.4 回归任务两层互补

- **端到端回归**：完整流程不退化（最接近生产，难定位失败步）
- **轨迹前缀回归**：冻结首个错误前的上下文，只测「下一步动作」——成本低、隔离单个策略/工具问题，**生产级 Agent 比端到端更重要**；答案定义为**可接受动作集合**（允许/禁止）而非唯一答案

### 2.5 LLM-as-a-Judge 的坑与解法

| 坑 | 现象 | 解法 |
|---|---|---|
| 长度偏差 | 长回答得分偏高 | Rubric 显式罚冗长/限长度/审计评分与长度相关性 |
| 同源模型（Goodhart） | Agent 与评判模型同家族 → 钻评判偏好盲区 | **多源异构评判**（不同家族 LLM 分别评，偏见正交难同时欺骗） |
| 位置偏差 | 评判偏向先出现的候选 | 交换顺序各评一次取平均，或两次一致才计入 |
| 评判者校准缺失 | 评分不可信 | 放量前建 100-200 例金标集，kappa>0.7 才启用；Rubric/评判模型更新后重新校准 |

### 2.6 统计显著性（防自证）

- SE(p)≈√(p(1-p)/n)——100 例 70% 成功率，95% CI ≈ ±9pp；「73% vs 70%」不足以支持切换
- **配对分析**：逐题记录谁胜出，用 McNemar/配对 bootstrap（不是直接相减两个独立成功率）
- 每个配置多随机种子（3-5 次），报告均值+波动范围；多重比较收紧阈值
- 判据：分差超噪声 + 配对成立 + 可复现，才值得切换

### 2.7 Benchmark → 改进闭环（迭代方法论）

1. 分数下降先查评测系统再动 Agent
2. 读报告先找失败簇（按任务/能力标签聚集），别盯总分
3. 一轮只改一个变量（AndroidWorld 三轮：H1 加提示无效→H5 换 accessibility feed 100% 但 token 2.5×→H5C 精简节点 100% 且 token 0.5×）
4. 小样本只够决定下一步，不够下结论——4/4 不能写成整体 100%，先过完整复测
5. 好报告写清：结论适用哪里/哪些底线没过/下一轮验证什么

### 2.8 内部评估基础设施

- **消融开关**：每个特性可独立关闭（启动路径极早期注入），定期跑消融发现「特性债务」
- **AB 测试**：多臂而非二元；**区分机制指标与目标指标**（改的是机制，关心的是目标，问「是同一个吗」）；**护栏指标**（不能变差的底线）
- **双层特性开关**：编译时（物理移除）+ 运行时（服务端下发）
- **提示词敏感性**：系统提示确定性渲染 + 版本化快照 + 每次变更跑回归（像代码 CI）
- **可观测性回流**：trace/span 树（OpenTelemetry/OpenInference）；生产轨迹→失败筛选→脱敏→沉淀为回归用例（评估集从静态变活资产）

### 2.9 成本分析

- **上下文累积效应**：每轮重发全部历史+工具返回，1k+2k+3k=6k 而非 3k；工具返回占输入大头（八轮任务 9,544/20,700）
- **KV Cache 与压缩非加性**：稳定前缀单开省 28.3%；压缩历史单开省 17.5%；**合开只省 30%（非 45.8%）**——压缩会缩短可命中缓存的前缀，必须完整任务一起实测
- 选型指标：TTFT/思考延迟/p95 尾部延迟/预算-能力曲线（RE-Bench：短预算领先不能外推长程）

## 三、常见坑

1. 用 Pass@k 评估可靠性场景（应该用 Pass^k）
2. 分数下降直接调模型，不查评测系统/环境资源
3. 用单次 4/4 当整体结论
4. 评判模型与 Agent 同源（Goodhart 钻空子）
5. 只评结果不评轨迹（「说了」当「做了」）
6. 忽略统计显著性，凭「感觉变好了」切换

## 四、工程判据（决策清单）

- **要上线可靠性功能**（支付/权限/部署）→ 指标用 Pass^k，设一票否决项
- **不知道瓶颈在模型还是 Harness** → 先跑模型替换实验，再跑消融
- **分数下降** → 第一步查评测系统（环境/用例/bug），第二步找失败簇，第三步才动 Agent
- **要换评判/评估方法** → 先建金标集校准（kappa>0.7），再放量
- **要省成本** → KV Cache 与压缩分开实测，别按单开数据相加估算
- **要做自我评估** → 先搭消融开关 + 轨迹前缀回归 + 生产轨迹回流
