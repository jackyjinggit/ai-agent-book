## 一、核心认知

1. **多 Agent 系统两个核心维度**：上下文是否共享（信息可见性）+ 协作拓扑（谁指挥谁）。
2. **多 Agent 不一定优于单 Agent**——纯文本推理任务上，等量计算下多 Agent 辩论并不优于单 Agent；多 Agent 的真正优势在**并行、分工、外部世界隔离**，不是「人多力量大」。
3. **共享上下文的悖论**：信息透明利于协调，但同质趋同扼杀多样性（三体人思维透明、回形针思想实验）——效率与多样性要刻意平衡。
4. **六种失败模式是设计的必查清单**：并发冲突、错误级联、同质趋同、互相扯皮、循环失控、理解债与认知投降。

## 二、可操作框架

### 2.1 分类框架

| 维度 | 选项 |
|---|---|
| 上下文 | 共享（同一视角）vs 不共享（各看各的） |
| 拓扑 | 对等 / 管理者（中心化）/ 去中心化 / 跨组织（A2A 协议） |

### 2.2 协作模式

- **对等协作**：相互制衡与迭代改进（如提议者-审核者扩展到 Agent 间）
- **管理者模式**：中心化协调——一个 Leader 拆任务、合并结果；注意「一个成功全员停止」的级联终止机制
- **去中心化**：无中心，靠协议/市场机制（Pinchwork、RentAHuman：Agent 花钱雇 Agent/人类）——质量仲裁与防劣币驱逐良币是难题
- **不共享上下文的通信**：Agent 眼中的文件系统（共享文件作为通信媒介）+ Agent 间消息控制

### 2.3 六种失败模式（必查清单）

| # | 失败模式 | 表现 | 对策方向 |
|---|---|---|---|
| 1 | 共享文件系统并发冲突 | 同时写同一文件 | 乐观锁/文件锁/治理 |
| 2 | 错误的级联放大 | A 的错误被 B 当事实 | 证据标注、独立验证 |
| 3 | 同质趋同 | 所有 Agent 想到一块 | 多样性注入、隔离信息 |
| 4 | 互相扯皮 | 责任不清推诿 | 明确分工与验收 |
| 5 | 循环失控 | A 改 B 改 A… | 终止条件、级联终止 |
| 6 | 理解债与认知投降 | 下游 Agent 不质疑上游 | 可质疑机制、越权申诉 |

## 三、常见坑

1. 为了「多 Agent」而多 Agent（等量计算无收益还引入协调成本）
2. 共享上下文 + 同目标 → 同质趋同，多样性归零
3. 管理者模式下子 Agent 结果互相失效（无级联终止，浪费算力）
4. 共享文件系统无锁/无治理 → 并发冲突 + 命名空间污染 + 单点故障
5. 市场机制无仲裁 → 质量争议 + 劣币驱逐良币

## 四、工程判据（决策清单）

- **要不要多 Agent** → 先确认收益来自并行/分工/隔离；纯推理任务单 Agent 即可
- **共享 vs 不共享上下文** → 需要全局一致选共享（接受趋同风险），需要多样性/隔离选不共享
- **选拓扑** → 任务可拆解、要强控制选管理者；要弹性选对等/去中心化；跨组织用 A2A
- **上线前查六失败模式** → 逐条过：锁、验证、多样性、分工、终止、质疑机制
- **多 Agent 出问题** → 先定位是协调层（拓扑/通信）还是任务层（单 Agent 能力）
