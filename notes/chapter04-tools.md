# 精读笔记 · 第 4 章《工具》

> 来源：李博杰《深入理解 AI Agent：设计原理与工程实践》第 4 章（结构精读）
> 本文为加工产物：基于章节结构与关键要点提炼，供落地实践复用

## 一、核心认知

1. **工具 = Agent 的手脚**——工具设计质量直接决定 Agent 能做什么、做得对不对；工具是 Harness 工程里投入产出比最高的部分之一。
2. **工具设计的本质是接口设计**——粒度、通用性、描述、参数保真，四件事决定工具是否「好用、不乱用、不传错」。
3. **MCP 把工具定义从框架解耦**——标准化带来生态，但流式输出/双向通信/有状态会话等复杂交互难以在标准协议中表达（MCP 的扩展空间）。
4. **「工具爆炸」是真实问题**——Agent 面对数千工具时选择精度下降；解法不是堆工具，是主动工具发现 + Skills 渐进式披露。

## 二、可操作框架

### 2.1 工具分类

| 类 | 作用 | 例子 |
|---|---|---|
| 感知工具 | 获取世界信息 | 搜索、抓取、多模态感知 |
| 执行工具 | 改变世界状态 | 文件/命令/API/写库 |
| 协作工具 | 与人和系统协作 | 通知、审批、会议 |

### 2.2 工具设计五原则

1. **能力表达形式**：专用工具 vs Skill + 通用执行器——专用更准、通用更省；按使用频率和确定性选
2. **粒度权衡**：整合（少而全）vs 分离（细而专）——整合降调用成本、分离提复用
3. **通用性设计**：参数少而语义化，避免「只能干一件事」
4. **工具描述的艺术**：描述决定模型会不会用、什么时候用——写清输入输出、适用场景、边界
5. **参数传递保真**：序列化/转义错误是工具调用的隐性杀手（字节→工具返回→序列化→模型→匹配，逐层可能丢）

### 2.3 主动工具发现与 Skills

- **模型原生工具发现**：让模型自己从描述里选工具（依赖描述质量）
- **Skills 渐进式披露**：工具定义按需加载——Agent 判断需要时才展开完整内容，对抗工具爆炸

### 2.4 执行-验证-反馈闭环

- 操作后立即自动验证（如写代码后跑 linter）——把「做完」变成「做对」
- 验证成本 > 操作本身价值的场景不适用

## 三、常见坑

1. 工具描述模糊 → 模型误用/不用
2. 参数序列化丢保真 → 静默传错（归因困难：模型对、传输层错）
3. 工具爆炸 → 选择精度下降
4. MCP 生态同名工具行为差异，模型无法感知利用
5. 只执行不验证 → 错误累积到最终结果才发现

## 四、工程判据（决策清单）

- **设计新工具** → 先写描述（适用场景/输入输出/边界），再定粒度
- **工具太多** → 用渐进式披露 + 主动发现，别全量灌上下文
- **工具调用出错** → 沿「原始字节→返回→序列化→模型输入→输出→匹配」逐层找首个分歧
- **高风险操作** → 执行后强制验证闭环（linter/校验/回读）
- **MCP 选型** → 功能重叠的工具按「描述质量 + 行为一致性」优先
